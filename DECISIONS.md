# Decisions

One row per call: the question, the options, the trade-off, and what we chose. Newest at the bottom.

| # | Date | Question | Options | Trade-off | Choice |
|---|---|---|---|---|---|
| 1 | 2026-11-23 | Which community? | Anki forums, a subreddit, Hacker News | Anki's Discourse has a public JSON API, steady volume (~60 topics, ~370 posts a week), and clear categories. Reddit's API is gated; HN is too broad for "themes". | Anki forums |
| 2 | 2026-11-23 | Where do vectors live? | Dedicated vector DB (Pinecone, Qdrant), Postgres + pgvector | A dedicated store scales to hundreds of millions of vectors but is one more service, and you lose joins/date filters next to the vectors. We have tens of thousands of chunks. | Postgres + pgvector |
| 3 | 2026-11-23 | Stack | Rails 8, Python | Rails is where I can explain every line. pgvector has first-class Rails support via the `neighbor` gem. | Rails 8.1 + Hotwire, no React |
| 4 | 2026-11-23 | How do reviewers run it? | Docker for everything, Docker for Postgres only, no Docker | Full Docker means no Ruby needed; DB-only Docker is faster for Rails devs. Supporting both costs one compose file. | Both: `docker compose up`, or `docker compose up -d db` + `bin/setup` |
| 5 | 2026-11-23 | Ruby version | 3.3.6, 3.3.14 | Brakeman flags a critical CVE in 3.3.6. CI and Docker use 3.3.14. | 3.3.14 |
| 6 | 2026-11-23 | Background jobs | Sidekiq + Redis, Solid Queue | Solid Queue is Rails 8's default and stores jobs in Postgres: no Redis to run. It also has recurring schedules built in. | Solid Queue (also in development) |
| 7 | 2026-11-23 | How to crawl Discourse | Walk every topic (`/t/{id}.json`), page `/posts.json` | `/posts.json` includes raw text and costs ~7 requests a week. Walking topics costs 60+ requests and handles long threads with extra pages. | `/posts.json?before=` |
| 8 | 2026-11-23 | Avoid duplicates on re-runs | Delete-and-reload, upsert by forum id | Upserts make every run safe to repeat and let weekly windows overlap by a day. | Upsert on `discourse_id` |
| 9 | 2026-11-23 | How polite to be | No limit, 1 req/s, cached responses | 1 req/s means a 12-week backfill takes ~2 minutes, which is fine. Disk caching deferred. | 1 req/s, User-Agent, back off on 429 |
| 10 | 2026-11-23 | Backfill depth | 2, 12, 52 weeks | 12 weeks gives history for predictions and "look-alike" retrieval; 2 weeks keeps reviewer setup to ~20 seconds. | 12 for the demo, 2 by default in `bin/setup` |
| 11 | 2026-11-23 | What to drop at ingest | Nothing, non-regular posts, tiny posts too | Dropping tiny posts here would make our counts disagree with the forum's. | Drop moderator actions, hidden, deleted; skip tiny posts later, at chunking |
| 12 | 2026-11-23 | Chunk size | Whole post, ~150 words, one sentence | The model reads ~256 word-pieces; 150 words + header fits. Smaller loses context; bigger blurs ideas and truncates. | 150 words, 30-word overlap |
| 13 | 2026-11-23 | Give chunks context | Nothing, header line, store separately | A three-line header (topic, category, date) costs ~20 tokens and makes each chunk understandable alone, for both the vector and the model. | Header on every chunk |
| 14 | 2026-11-23 | Minimum post length | 0, 5, 12, 25 words | 12 words drops "thanks, that worked!" (~10% of posts) but keeps short real answers. | 12 words |
| 15 | 2026-11-23 | Avoid re-embedding | Re-embed everything, compare text, store a hash | A SHA-256 per chunk is cheap to compare and makes every run incremental. | Content hash |
| 16 | 2026-11-23 | Embedding model | Hosted (OpenAI, Voyage), local MiniLM | Local needs no key and no cost; reviewers only need one key (Anthropic). Lower quality than large hosted models, fine for forum posts. | all-MiniLM-L6-v2 via `informers`, 384 dims |
| 17 | 2026-11-23 | Vector index | None (exact scan), IVFFlat, HNSW | An exact scan is fine at 5k chunks but does not scale; IVFFlat needs data before it is built. HNSW is fast, accurate and can be built on an empty table. | HNSW, cosine |
| 18 | 2026-11-23 | Stop one thread filling the results | Nothing, max N per thread, MMR | One long thread took 4 of the top 5 (step 4). A per-thread cap is one line and easy to explain; MMR also catches two threads saying the same thing but needs a weight tuned. Measured: threads covered in the top 8 went from 3.9 to 5.5. | Max 2 chunks per thread |
| 19 | 2026-11-23 | When is a chunk "not relevant"? | Always top-k, a cosine-distance cut-off | Top-k always returns something, even for off-topic questions. A cut-off lets the report say "not enough evidence". On our eval, 0.6 is the lowest value that finds every query; off-topic queries never came closer than 0.71. | Cut-off 0.6 |
| 20 | 2026-11-23 | Date filter plus approximate index | Post-filter at default settings, raise `ef_search`, exact scan, pgvector 0.8 iterative scan | HNSW looks at 40 candidates and filters after, so a 1-week window over 12 weeks can come back short. Raising `ef_search` to 200 works on any pgvector version at a small speed cost. | `SET LOCAL hnsw.ef_search = 200` |
| 21 | 2026-11-23 | Vector-only or hybrid search | Vector-only, vector + full-text | Our queries are about themes, not exact strings. Hybrid helps for version numbers and error codes. Deferred; the eval set will show if it is needed. | Vector-only |
| 22 | 2026-11-23 | Log retrievals | Not at all, log lines, tables | Tables make "most retrieved post" and "how often a query finds nothing" one SQL query, and show what each A/B arm saw. | `retrievals` + `retrieval_hits` |
| 23 | 2026-11-23 | What is one point when clustering? | Chunk, post, thread | A theme should be several threads about one thing. Clustering posts lets one 100-reply thread become a "theme". A thread's vector is the average of its chunks that week (`avg(embedding)` in SQL). | Thread |
| 24 | 2026-11-23 | Clustering method and k | k-means with fixed k, k picked by silhouette, k from the week's size, HDBSCAN | k-means is simple and, seeded, deterministic. HDBSCAN finds k itself but has no Ruby library. Measured k = 4-12 on three weeks: silhouette is flat (0.05-0.12), so there is no natural k; a fixed 8 left 3 one- or two-thread themes in a quiet 56-thread week. Cost: one-off threads join the nearest theme, so some themes are mixed. | Spherical k-means, seed 42, k = threads / 12 kept between 4 and 8 |
| 25 | 2026-11-23 | Who counts, who names | LLM does both, SQL counts + LLM names | LLMs miscount; SQL is exact. The LLM only labels and summarises a cluster from 12 titles and 5 excerpts. | SQL counts, the LLM names |
| 26 | 2026-11-23 | How to call an LLM | Call a vendor SDK where needed, one provider-neutral interface with adapters; free text or a JSON schema | Callers depend on `Llm` (`json(system:, prompt:, schema:)`), injected, so specs use a fake and the provider is a setting (`LLM_PROVIDER`). JSON-schema output returns a parsed Hash. The one adapter so far is Anthropic (official gem, structured outputs, server-side fallbacks); settings are `LLM_PROVIDER`, `LLM_API_KEY` and `LLM_MODEL`, so switching provider changes no variable names. Low effort for naming. | `Llm` interface, Anthropic adapter by default |
| 27 | 2026-11-23 | What is "a week"? | Rolling 7 days, Monday to Monday | Calendar weeks match Postgres `date_trunc('week')` and make "last week" and "next week" unambiguous for predictions and backtests. | Monday to Monday (`Week`) |
| 28 | 2026-11-23 | How to retrieve for a report | One query for the whole week, one query per theme | A single query favours the loudest topic. One query per theme (label + summary) gives every section its own evidence. 6 themes x (6 + 3) chunks is about 7,000 tokens of prompt. | Per theme: 6 from the week, 3 from the 12 weeks before |
| 29 | 2026-11-23 | How to keep the report honest | Trust the prompt, a judge model, checks in code | Numbered evidence, citations after every claim, word-for-word quotes and SQL-only numbers make errors detectable; code checks citations and quotes for free. A judge for "is this claim supported" comes in the A/B step. | Cite-or-omit prompt + `Reports::Grounding` |
| 30 | 2026-11-23 | What if nothing relevant is found? | Write anyway, skip the call | Asking a model to write with no evidence invites invention. | No model call; report says "Not enough evidence"; themes with nothing to cite are listed, not written |
| 31 | 2026-11-23 | Do reports become searchable sources? | Embed reports, keep them separate | Retrieving its own past claims would let the report drift from what the forum said. | Reports are outputs only, never chunked |
| 32 | 2026-11-23 | How will the A/B arms differ? | Separate builders, one builder with a pluggable evidence source | Same prompt, schema, model and checks for every arm, so only the context differs. | `evidence_source:` on `Reports::Builder` |
| 33 | 2026-11-23 | How to see a theme's trend | Re-run clustering every week and match themes, count posts near this week's centre | Matching clusters across weeks is fiddly; distance to the centre is one SQL query per week. At 0.45 every theme looked big (all chunks share a header); at 0.35 the 26.10 release spike (4 → 38 posts) stands out. | Posts within cosine distance 0.35 of the centre, 6 weeks |
| 34 | 2026-11-23 | Which events can predictions use? | None, an external release calendar, forum threads | Beta and release threads are already in the forum and citable. Titles with "update" were dropped: too many "broke after update" help threads. | Beta Testing / Announcements threads and titles with release or beta, last 14 days |
| 35 | 2026-11-23 | What makes a prediction useful? | Free text, structured and checkable | A claim checkable against next week, a cited reason, a basis and a confidence can be scored by the backtest. Only data from before the week's end is used, so backtests are honest. | `predictions[{claim, reasoning, basis, confidence, theme}]` in the report call |
| 36 | 2026-11-23 | How to score a prediction | Keyword matching, a human, an LLM judge shown the next week's posts | Predictions are sentences ("fewer toolbar threads"), so string matching cannot score them and a person does not scale to a weekly run. A judge is shown the posts closest to each claim from the week it was about, plus exact counts for that week. | LLM judge with retrieved evidence |
| 37 | 2026-11-23 | Keep the judge honest | Trust its verdict, require citations checked in code | A "happened" or "partly" verdict must cite a post that was really shown; otherwise it is recorded as "no_evidence" and left out of the hit rate. A judge that cannot point at anything has not judged. | Citations checked in code, demote if none |
| 38 | 2026-11-23 | Verdict scale | Yes/no, four verdicts | Many claims are half true. happened = 1, partly = 0.5, did_not_happen = 0; "no_evidence" (the posts do not let you tell) is counted separately so quiet topics do not drag the score down. | happened / partly / did_not_happen / no_evidence |
| 39 | 2026-11-23 | How to prevent peeking | Re-create the database as of an old date, trust the code, bound every query by the report's week | Every signal, retrieval and count the report uses is bounded by the end of its week, so writing a report for an old week cannot see what came next. A spec plants a post in the following week and checks it never reaches the prompt or the saved evidence. Only the scorer looks forward. | Bounded by construction, tested with a planted post |
| 40 | 2026-11-23 | What is a backtest run | Re-write every report, reuse stored ones | A stored report for week W was already written from pre-W data, so reusing it is as honest as rewriting it and costs nothing. | Reuse stored reports and judgements, build only what is missing |
| 41 | 2026-11-23 | The three A/B arms | RAG vs nothing, RAG vs paste-all, all three | The challenge asks for "without RAG". Paste-all is the stronger rival: a week is ~50,000 tokens, which fits. All three show what retrieval buys and what it costs. Paste-all gets the same themes and SQL signals as RAG; it differs in getting every chunk of the week instead of a few per theme, and no posts from earlier weeks. | none, paste_all, rag; same schema and checks |
| 42 | 2026-11-23 | What does "no context" mean | Themes and counts only, nothing | The point is "just ask an LLM": the prompt holds only the week's dates and a plain system prompt that admits it has no posts. Giving it our themes would leak our pipeline into the baseline. | Dates only |
| 43 | 2026-11-23 | How to judge A/B quality | One overall score from a model, code checks only, code checks plus two small judges | Code checks (valid citations, verbatim quotes, uncited sentences) are objective but cannot tell if a sentence means what its source says. A support judge reads each sentence with only the posts it cites. A blind ranker, shown shuffled reports and exact facts about the week, scores coverage, accuracy, specificity and usefulness. | Code checks + support judge + blind ranker |
| 44 | 2026-11-23 | Which model judges | The writer, a different model | A model can favour its own style. `LLM_JUDGE_MODEL` lets the judge differ; it defaults to the writer's model so one key and one setting still work. | `LLM_JUDGE_MODEL`, default the writer |
| 45 | 2026-11-23 | Where judgements live | A table per kind, one table | Prediction scores, support checks and rankings all answer "what did a judge conclude about a report", and the charts read them together. | One `judgements` table with a `kind` |
| 46 | 2026-11-23 | Charts without React | A charting gem, server-drawn SVG, vendored Plotly driven by Stimulus | The server describes each figure as data (testable in RSpec); one small Stimulus controller hands it to Plotly. The "basic" Plotly bundle (bars, scatter) is 1 MB and vendored, so charts work offline and need no build step. | Plotly basic bundle, `plot_controller.js` |
| 47 | 2026-11-23 | Flattening the embeddings | PCA, t-SNE, UMAP | PCA is deterministic, explainable in a sentence, and short enough to write in Ruby. t-SNE and UMAP separate clusters better but need a library and are not repeatable run to run. One dot per thread (the average of its chunk vectors) keeps the map readable. | PCA over thread vectors |
| 48 | 2026-11-23 | Retrieval stats | A separate stats store, read the retrieval log | Step 5 already logs every search and hit; "most retrieved chunk" and the distance spread are one query each. | Read `retrievals` and `retrieval_hits` |
| 49 | 2026-11-24 | What exactly does paste-all paste? | Every chunk plus our themes, every post once with no themes | Chunks overlap by 30 words and repeat a header, which inflated paste-all's cost by ~40%, and handing it our themes leaked the RAG pipeline into the rival. The fair rival is "paste the week": each post once, cleaned like chunks are, each thread title once, plus the same exact counts. Supersedes part of #41. | Each post once, no themes, no trend or release signals |
| 50 | 2026-11-24 | Which model judged the sample run | Opus (the writer), Sonnet | A model may favour its own writing. Sonnet is a different model and cheaper. | `LLM_JUDGE_MODEL=claude-sonnet-5-5` |
| 51 | 2026-11-24 | Where does a backfill start? | N x 7 days ago, the Monday N full weeks back | Starting mid-week left the oldest week partial: its low count made the baseline look small ("activity is up") and trend lines started with fake zeros. A Monday start keeps every week whole; `Ingest::Coverage` also leaves out a partial oldest week (older data, or a crawl that began mid-week) from counts, trends and the week list. | Monday start, plus `Ingest::Coverage` |
| 52 | 2026-11-24 | What if the crawl fails during setup? | Abort setup, start the app anyway | A forum outage or network blip should not stop a demo: stored data and reports still work. The client now retries timeouts and 5xx as well as 429. Restarts only re-crawl the last day when the data already covers the backfill. | Retry, then warn and start |
| 53 | 2026-11-24 | How many chunks per theme, and which | 6 each, a budget shared by theme size, plus each theme's busiest threads | The A/B judge found RAG missed the week's second-biggest thread. Cause: every theme got 6 chunks (at most 6 of a 33-thread theme's threads), and the theme's query lands near its centre, so a big thread at the edge lost. Now 36 chunks are shared by each theme's share of the threads (3 to 12 each), and each theme's 2 busiest threads by post count (SQL) always get their chunk closest to the query (vectors). +17% input tokens; judge coverage 3 → 5. | Size-shared budget + 2 busiest threads per theme |
| 54 | 2026-11-24 | How does the app know which model made a vector? | Trust that it never changes, check the length only, stamp the model on every chunk | Two models' vectors cannot be compared even at the same length, and the fixed `vector(384)` column only catches a different length, as a database error mid-batch. A stamp lets the Embedder re-embed stale rows and the Retriever compare like with like; a guard checks lengths before any work. Cost: one string column. | `chunks.embedding_model` + `Embeddings::Guard` |
| 55 | 2026-11-24 | How many themes does the report write up? | The top 6, every theme with 2+ threads (up to k-means' 8), top 6 plus an "also discussed" list | k-means already caps a week at 8 themes, so a second cap of 6 silently dropped themes 7 and 8 (one 8-thread theme on 2026-11-16, ~8% of the week) without even naming them. Writing all of them means one rule and full coverage, for up to 2 more sections and ~10-15% more prompt on busy weeks; quiet weeks make 4-5 themes and do not change. The published A/B sample was run with 6. | Every theme with 2+ threads; `THEMES` follows `Themes::Finder::K_RANGE.max` |
| 56 | 2026-11-24 | How does the UI let someone search the forum? | Search by meaning in its own tab (reuses the report's retriever), keyword search, filters | The reviewer should be able to try retrieval without an LLM key. Reusing `Search::Retriever` means the same cut-off (0.6) and per-thread cap (2) apply, so search shows what the report could cite, and every search is logged for the stats page. No date window, no filters yet. Tabs group the pages: report, search, charts, flashcards (placeholder). | Own tab, same retriever, purpose `search` |
| 57 | 2026-11-24 | Should the crawl and the evaluations be in the interface? | Rake tasks only, buttons for everything, buttons plus the same code behind rake | A reviewer should be able to run the whole pipeline from the browser. The bodies of the rake tasks moved to `Pipeline::Runner` so both paths run identical code; results are stored in `job_runs`. Tasks that cost money confirm first, need a key, and refuse a second run while one is active. Evaluation stays manual: it costs money and only needs re-running when something changes. | Buttons + shared `Pipeline::Runner`, background `PipelineJob`, manual refresh |
| 58 | 2026-11-24 | How to make the UI understandable on first use | Longer help text, a guided tour, show the state and gate the buttons | People were confused by what the app had (2 weeks vs 12) and what each button needed. Showing state (a data line on every page, a Data tab) and saying why a button is disabled answers those questions where they arise, with less text to read. Crawling moved off the Evaluate tab because it is not an evaluation. Pages refresh while work runs, instead of a live channel (Turbo Streams): simpler, good enough for minute-long jobs. | Status line + Data tab + gated buttons + meta refresh |
